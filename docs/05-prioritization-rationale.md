## 1. หลักคิด

ทีมใช้ 4 คำถามในการพิจารณา Priority ของแต่ละ Requirement:

1. **Value:** Requirement นี้ช่วยแก้ปัญหาหลักให้ใคร และสร้างประโยชน์อย่างไร?
2. **Risk:** หากไม่มี Requirement นี้ จะเกิดความล่าช้า ข้อมูลไม่ครบ งานซ้ำ หรือการตัดสินใจผิดพลาดหรือไม่?
3. **Urgency:** Requirement นี้จำเป็นต่อ Workflow หลักของระบบในรุ่นแรกหรือสามารถทำภายหลังได้?
4. **Dependency:** Requirement นี้ต้องรอข้อมูลจาก Stakeholder, Policy, Authority หรือข้อมูลเพิ่มเติมหรือไม่?

## 3. สิ่งที่ไม่ได้เลือกเป็น requirement ทันที

| สิ่งที่พบใน Week04 | เหตุผลที่ยังไม่กำหนดเป็น Requirement |
|---|---|
| พัฒนา LINE Bot หรือ Mobile App ควบคู่กับเว็บ | เป็นเพียง preference ช่องทาง และเกินขอบเขตเวลาพัฒนา (Out of Scope) |
| แจ้งเตือนทุกครั้งที่สถานะเปลี่ยนผ่าน SMS หรือ Push Notification | มีค่าใช้จ่ายสูงและยังไม่ยืนยันว่าทุกสถานะจำเป็นต้องแจ้งเตือนฉุกเฉิน |
| ลงโทษด้วยการปรับเงินกรณีส่งคืนอุปกรณ์สาย | ยังไม่มีเอกสารนโยบายหรือระเบียบการเงินรองรับ |
| ระงับสิทธิ์ถาวรกรณี No-show ครบ 3 ครั้ง | เป็นมาตรการที่ตึงเครียดเกินไป และยังไม่มีกระบวนการรองรับการอุทธรณ์ |
| ให้สิทธิ์ Walk-in แทรกคิวได้ทันทีโดยไม่ต้องผ่านระบบ | อาจทำให้เกิดข้อขัดแย้งกับผู้ที่รอคิวในระบบ และขัดกับหลักการ Record ออนไลน์ |
| บังคับใส่อาหาร/เครื่องดื่มที่นำเข้าห้องในฟอร์มจอง | เพิ่มภาระการกรอกข้อมูลเกินความจำเป็น และเจ้าหน้าที่ตรวจหน้างานได้อยู่แล้ว |

## 4. บทเรียนสำหรับนักศึกษา
- Priority สูงไม่ได้หมายความว่า Requirement สมบูรณ์แล้ว
- Requirement อาจมีความสำคัญต่อระบบ แต่ยังต้องตรวจสอบรายละเอียดเพิ่มเติมก่อนนำไปพัฒนาจริง
- อย่าเปลี่ยนข้อเสนอของ Stakeholder ให้เป็น Requirement ทันที
  - เช่น การใช้ LINE Bot หรือ Mobile App เป็นเพียงข้อเสนอเรื่องช่องทาง ต้องตรวจสอบความต้องการที่แท้จริงก่อน
- ถ้ายังไม่มี Evidence หรือ Policy ที่ยืนยัน ไม่ควรเดา
  - เช่น จำนวนวันจองล่วงหน้า, โควตาชั่วโมง, penalty หรือเกณฑ์ No-show ควรบันทึกเป็น Open Question หรือ Issue
- Requirement ที่ยังมีข้อมูลไม่ครบสามารถเก็บไว้เป็น Needs Follow-up ได้
  - ไม่จำเป็นต้องตัดทิ้ง เพียงระบุว่าต้องตรวจสอบอะไรและควรถามใคร
- Issue ที่ยังไม่มีหลักฐานเพียงพอควรอยู่ใน Hold
  - เพื่อป้องกันการสร้างกฎหรือข้อกำหนดจากความคิดเห็นของทีมเอง
- ทุก Requirement ควร Trace กลับไปยัง Evidence หรือ Need ได้
  - เพื่อให้ตรวจสอบได้ว่า Requirement นี้เกิดจากข้อมูลอะไร และใครเป็นผู้ให้ข้อมูล
- Backlog ที่ดีต้องบอกทั้ง “ทำอะไรต่อ” และ “อะไรยังไม่ควรทำ”
  - ช่วยให้ทีมวางแผน Week ถัดไปได้อย่างมีเหตุผล และลดการออกแบบระบบจากการคาดเดา
